High-level picture: what's the goal?

  • We want to find a safety violation: identify a bug in a program
  • We can often see this in terms of reachability:
    • Is it possible to reach / drive the program execution to an exploited state starting from its normal path of execution?

For example...

if (len < 64 && magic == 0x41424344) {
  memcpy(buf, input, len + 16);
}

We might ask...

Is there any input that reaches this point while violating a memory safety condition?

Many ways to identify safety violations

  • Computer science has explored many ways of finding (memory, etc.) safety violations
    • Testing
    • Fuzzing
    • Reachability-based program analysis / abstract interpretation / etc.
    • Symbolic execution
    • Program logics
  • All of these rely upon different formal foundations.
    • For example, abstract interpretation uses properties of lattices and monotonic functions defined over these lattices.
    • Meanwhile, symbolic execution uses SAT/SMT

Symbolic execution versus program analysis

Build with the arrow keys.

(0) The tree. Symbolic execution starts at the program entry and forks at every branch. Each path is a conjunction of branch conditions; the solver prunes branches whose condition is infeasible (the grey stub). Every path is trying to reach the exit.

(1) Two paths actually finish. One hits a bug: that is a real, reproducible finding, and it is the reason we run the tool. One reaches the exit: a single complete trace with no bug on it.

(2) Everything else is a partial trace. Budgets run out, solvers time out, the tree explodes. A partial trace that has not hit a bug is not a verdict about anything below it: the fog may hide a bug, or it may not. So "no bug found" is not "no bug". The explored paths are a subset of the real behaviors (explored ⊆ real), which is exactly the shape of testing. Dijkstra: testing shows the presence of bugs, never their absence.

(3) Program analysis flips the direction. Instead of enumerating runs, it computes a mathematical description of the program (an abstract domain, a fixpoint over a lattice, a dataflow solution) that is guaranteed to contain every real behavior (real ⊆ abstract). The blob is messy; the bubble is a simple shape the math can compute.

(4) If the bad states lie outside the bubble, they are provably unreachable: a proof, not a test. The price of the bubble being bigger than reality: bad states that fall into the gap are false alarms, possible in the abstraction and impossible in any real run.

Next lecture is program analysis proper. A CRS wants both kinds of evidence: real bugs from the testing side, proofs and pruning from the analysis side.

SAT versus SMT

Propositional SAT asks whether a Boolean formula can be made true.

(x∨y)∧(¬x∨z) (x \lor y) \land (\neg x \lor z) (x∨y)∧(¬x∨z)

  • Can use SAT to ask: "does a counterexample exist?". The variables are implicitly existentially quantified. So it's really, "does there ∃x,y,z.\exists x,y,z.∃x,y,z. s.t. the formula (x∨y)∧(¬x∨z)(x \lor y) \land (\neg x \lor z)(x∨y)∧(¬x∨z) is true?"

By contrast, SMT asks whether a formula is satisfiable modulo a first-order theory:

0≤n<64∧n+16>72 0 \le n < 64 \land n + 16 > 72 0≤n<64∧n+16>72

Here, the symbols ≤\leq≤, <<<, +++, and >>> appeal to a theory of arithmetic

  • Can't be all of arithmetic, that would be impossible (Gödel's incompleteness theorems)

Background: de Moura and Bjørner, "Z3: An Efficient SMT Solver," TACAS 2008; Barrett et al., "The SMT-LIB Standard."

Start the SMT section here. The verbal contrast should be: SAT knows only true/false structure. SMT additionally knows something about the objects being talked about.

How is SMT solving useful in vulnerability discovery?

Security questions often mix control flow with low-level data facts:

  • Can attacker input reach this branch?
  • Can a length arithmetic operation wrap around?
  • Can two pointers alias?
  • Can a string satisfy a parser's checks?

SMT is useful because these are not just Boolean questions. They involve machine integers, memory, strings, and path reachability.

The challenge is how to phrase our attack-relevant statements in the language of SMT

Is "SMT" really AI?

  • SAT solving is classic symbolic AI.
    • SMT solvers still incorporate aspects of SAT solving, e.g., DPLL(T), CDCL, clause learning, etc.
  • SMT solvers are an extension of SAT to first-order theories
  • What about modern LLMs? Do we really need SMT in the age of modern LLMs and tools?
    • As far as I know, this is an open question--one we will try to explore...

How SMT solving works, the 1000-foot view

  • SMT tries to build an assignment by guessing at unconstrained variables and then forcing implications. For example, if we guess x = 5 and we have x<0→y=5x < 0 \to y = 5x<0→y=5, we must have y=5y=5y=5

    • This is called propagation; in this case theory propagation, since we are appealing to the theory of arithmetic

  • A SAT engine explores the SAT fragment of the problem

  • Theory-specific solvers reason about specific theories: numbers, memory, equality

  • Learned explanations allow generalizing knowledge to learn from previous mistakes

Bjørner et al., Z3 Internals, §2.1.

Build with the arrow keys: (1) Boolean search hands the theory a set of assigned conditions. (2) The theory answers with consequences or a conflict. (3) A conflict explanation is kept in the learned-clause store and fed back into the search. The store holds results of learning; not every theory propagation becomes a stored clause immediately.

Introduce the Boolean engine as a search procedure that remembers why an attempt failed. CDCL means conflict-driven clause learning. A Boolean variable can stand for a whole condition such as n ≤ 64. Assigning that Boolean does not choose a value for n.

Many modern SMT engines combine CDCL with theory reasoning. DPLL(T) and CDCL are compatible descriptions at different levels. There are also specialized engines and reductions, including bit-blasting. Avoid suggesting every solver configuration has an identical architecture. The exchange is incremental, not a service called once after Boolean search has finished; the next slides show the interaction step by step.

A theory-specific conflict can yield a learned lemma

Barbosa et al., cvc5, §2.1.

Build with the arrow keys: (1) b = true is required by the query; the interval n > 80 appears, open at 80. (2) The search decides a = true; the interval n ≤ 64 appears, closed at 64. (3) The two intervals do not overlap: no integer satisfies both. (4) Arithmetic explains the conflict as the lemma ¬a ∨ ¬b; a and b are its premises, c is not involved. The axis is a viewing window, not an additional bound.

Use mathematical integers for n and tag. This example has no wraparound. It illustrates a solver query, not a complete vulnerability or a claim that a particular program is insecure.

The query requires n > 80 and at least one of n ≤ 64 or tag = 7. At the Boolean level, setting both a and b to true satisfies the query regardless of c. Arithmetic recognizes that no integer can satisfy those two length constraints together.

The theory-valid clause ¬a ∨ ¬b states that the two conditions cannot both hold. It excludes every assignment containing that inconsistent pair. It is stronger than merely rejecting one complete Boolean assignment. The explanation need not be a minimum inconsistent subset.

For an expert audience: distinguish this theory lemma from the clause CDCL ultimately learns. Here b is a root-level fact. Resolving ¬a ∨ ¬b with b yields ¬a. The next slide shows both steps. Retaining the theory lemma is a valid teaching presentation, but actual implementations may materialize reasons lazily and retain a different learned clause.

The solver's inner loop

Barbosa et al., cvc5, §2.1; theory interface.

Build with the arrow keys: (1) the theory lemma ¬a ∨ ¬b. (2) Resolving it with b gives the learned clause ¬a; the optional level tags show b at level 0 and a at level 1. (3) Backtrack: the decision a = true and its theory assumption go away; b and the learned clause stay. (4) Propagate ¬a from the learned clause, then c from a ∨ c. (5) The candidate n = 81, tag = 7 goes to the final theory checks. (6) The checks pass: SAT, one satisfying input among many. Press down for the optional branch where arithmetic propagates ¬a before any decision is made.

Continue from the previous slide. Since b holds at decision level zero, conflict analysis can derive the unit clause ¬a. Backtrack to level zero, undo the decision a, and propagate ¬a. The original clause a ∨ c then forces c. Only after the theory checks succeed does the figure present n = 81, tag = 7 as an example model.

Define propagation as drawing a forced conclusion and a decision as making a choice. Backjumping can skip irrelevant decisions. This small example has just one decision, so it does not visually demonstrate skipping multiple levels.

The solver repeatedly alternates Boolean propagation with scheduled theory work. It need not run every expensive theory procedure after each assignment. Lightweight checks operate on partial assignments. Stronger checks can generate more lemmas when a candidate model is available. A Boolean satisfying assignment alone is insufficient for an SMT SAT result. Resource limits or incomplete procedures may produce unknown.

For an expert audience: a propagated literal has a reason that conflict analysis can request. Theory state must track backtracking correctly. Learned clauses survive search backtracking when valid in the retained assertion context. Search backtracking is distinct from an application's push/pop of assertions. Restarts and clause deletion are additional policies, omitted from the drawing for clarity. The loop is schematic, not an exact call graph: final checking, propagation, and decision heuristics do not run in one universal fixed order across solvers.

From concrete execution to symbolic execution

Concrete execution

input = "AAAA"
x = 0x41414141
branch: x == 0xdeadbeef  // false

One run. One answer.

Symbolic execution

input = α0 α1 α2 α3
x = concat(α0, α1, α2, α3)
branch condition: x == 0xdeadbeef

A set of inputs at once.

Now the question is not "what happened on this run?" It is: is there any input that makes the branch go the other way?

Classic system: Cadar, Dunbar, and Engler, "KLEE," OSDI 2008.

This is the conceptual bridge from fuzzing to symbolic execution. Fuzzing tries many concrete inputs. Symbolic execution reasons about a set of inputs at once.

Path conditions

A path condition is the conjunction of branch decisions needed to reach a program point.

if (n < 64) {
  if (tag == 0x1337) {
    sink(buf[n + 8]);
  }
}

Path to sink:

n<64∧tag=0x1337 \text{n} < 64 \land \text{tag} = 0x1337 n<64∧tag=0x1337

Potential out-of-bounds query:

n<64∧tag=0x1337∧n+8≥∣buf∣ \text{n} < 64 \land \text{tag} = 0x1337 \land \text{n} + 8 \ge |\text{buf}| n<64∧tag=0x1337∧n+8≥∣buf∣

This is examinable. Students should be able to write a path condition and then add a safety-violation condition.

Figure: building a path condition

Step through with the arrow keys: (1) choose n < 64, (2) choose tag == 0x1337, (3) add the bug condition n + 8 >= 64, (4) solve: sat, n = 56, tag = 0x1337, (5) swap in n + 8 >= 1000: unsat.

Pedagogical behavior: students should see that the solver is not "finding bugs" by magic. It answers the precise query we formulate.

Useful theories for reverse engineering...

SMT-LIB is a uniform standard for defining SMT queries via S-expressions and allows us to reuse a variety of solvers via a simple, uniform interface.

For vulnerability identification, the most important theories are usually:

  • Bit-vectors: machine integers, overflow, shifts, masks
  • Arrays: memory as select and store
  • Linear arithmetic: sizes, bounds, counters
  • Strings / regexes: web input, parsers, validation logic
  • Uninterpreted functions: abstraction when exact behavior is unknown

Not every theory is equally important for every target. For example, strings / regex is much more useful for doing web exploitation, whereas bit-vectors are useful for binaries / C-style apps

Mention nonlinear arithmetic as theoretically expressive but often painful. For many binary-analysis examples, bit-vectors and arrays are the load-bearing theories.

Bit-vectors: machine arithmetic, not integers

  • C integers are fixed-width.

  • For example, in 8-bit unsigned arithmetic we have 250 + 10 = 4, because arithmetic is modulo 282^828

A vulnerability query may depend on exactly this behavior:

uint8_t total = len + header;
if (total < 64) memcpy(buf, input, len);

  • If len + header wraps, the check may validate the wrong quantity!

  • Thus, a bit-vector theory has to track the size of each bit vector, and operations must properly account for things like overflow, etc.

How SMT solvers work, roughly

Modern SMT solving often looks like:

  1. Boolean (SAT solver) search proposes an assignment
  2. Theory solver checks whether it makes sense
  3. If contradiction, theory solver explains the conflict and returns a "lemma"
  4. Boolean search learns, backtracks, and tries again

No need to do a full DPLL(T) lecture. Give just enough for students to understand why mixing theories can be hard and why the solver is not simply brute force over inputs.

Figure: DPLL(T) intuition

So the Boolean search learns: not all of A,B,CA, B, CA,B,C can be true.

Step through: (1) SAT chooses A = true, edge x < y appears. (2) B = true, edge y < z. (3) C = true, edge z < x. (4) the theory solver finds the red cycle and emits the learned clause ¬A ∨ ¬B ∨ ¬C. (5) SAT backtracks and sets C = false; the graph is consistent again.

Use this to make DPLL(T) visual without requiring the students to know the full algorithm.

What is a cyber-reasoning system?

Term I made up; but I mean a frontier-LLM-orchestrated pipeline which does the following...

  1. build and run a target
  2. explore behavior
  3. find suspicious states
  4. prove or demonstrate a vulnerability
  5. repair or mitigate it
  6. validate the result
  • My claim: cyber reasoning systems will become increasingly important for both defensive and offensive tasks

Why not just fuzz? Why not just symbolic execution?

Fuzzing is excellent when:

  • executions are cheap and coverage tracks progress
  • bugs are shallow enough to stumble into

It struggles when:

  • inputs are deeply structured or need semantic consistency
  • the useful path is guarded by narrow constraints or state sequences

Symbolic execution is excellent when:

  • the relevant path is narrow and the query is precise
  • constraints are within solver reach

It struggles when:

  • path explosion dominates or solvers time out
  • memory, system interactions, or a missing harness get in the way

A CRS allocates each engine where it has leverage.

The classic hybrid: Stephens et al., "Driller: Augmenting Fuzzing Through Selective Symbolic Execution," NDSS 2016.

Where fuzzing stalls is where symbolic reasoning, static analysis, and LLM guidance enter. Where symbolic execution explodes is where cheap concrete execution takes over. Driller is the canonical example of handing off between the two.

The handoff, concretely: hybrid fuzzing

Driller's loop (QSYM and SymCC made it fast)

  1. Fuzz. Mutation is nearly free; it finds every shallow path
  2. Stall. No new coverage; every queued input dies at the same branches
  3. Trace. Re-run a stalled input concolically: concrete values, but record the path condition as it goes
  4. Flip. At a branch the fuzzer never took, negate its condition and ask SMT
  5. Seed. SAT means the model is a new input. Push it into the fuzzer's queue; go to 1
if (hdr.magic != 0x41424344) return; // 1 in 2^32 by mutation
if (hdr.len > body_len)      return; // relation between fields
if (!json_parse(body, &doc)) return; // 10k-line parser
use(doc);                            // the bug is here
  • Fuzzer alone: stuck on line 1
  • + SMT: lines 1–2 fall in milliseconds; then the solver explodes inside the parser
  • + LLM (ChatAFL, HLPFuzz): writes a valid body; the fuzzer mutates from there
Symbolic execution is a subroutine here, not the driver: it is called only on the branches where its expensive query pays for itself, and its answer is still just a seed the fuzzer has to run.

Stephens et al., Driller, NDSS 2016; Yun et al., QSYM, USENIX Security 2018; Poeplau and Francillon, SymCC, USENIX Security 2020.

Vertical backup under the fuzz-versus-symbolic slide; press down if there is time, or when a student asks how the handoff actually works.

Driller (NDSS 2016) pairs AFL with angr. Its framing: a fuzzer explores freely inside a "compartment" of the program but cannot cross the wall between compartments, which is a specific check such as a magic value or a checksum. Concolic execution is invoked only when the fuzzer stalls, only on the inputs already in its queue, and only to cross that wall.

QSYM (USENIX Security 2018) made the concolic step fast enough for real programs by instrumenting native execution instead of interpreting IR, and added optimistic solving: when the whole path constraint is unsatisfiable (usually over-constraining from incomplete modelling), solve only the last branch's constraint and let the fuzzer check the result. Say this out loud: it is the guess-then-check pattern of the LLM systems, with a solver as the guesser, and it is the thesis of the lecture in one design decision.

SymCC (USENIX Security 2020) compiles the symbolic bookkeeping into the target with an LLVM pass, another order of magnitude faster.

The third line of the example is where all of them run out: a hand-written parser is thousands of branches deep and its internal state is not something the solver's theories describe well (HLPFuzz's complaint about incomplete semantics modelling and over-constraining). That is exactly the slot the LLM fills on the ChatAFL and HLPFuzz slides.

Why not just ask an LLM?

LLMs are useful for:

  • code comprehension
  • hypothesis generation
  • recognizing protocols and formats
  • explaining tool output
  • proposing harnesses or patches

Main idea: Guess / generate hypotheses with LLM, then check with tools to provide ground truth

  • Tests, symbolic execution, fuzzing (e.g., with seed generated by LLM)

ChatAFL — LLM-guided protocol fuzzing

NDSS 2024, Meng et al., built on AFLNet. The LLM has already read the RFCs: ask it narrow questions, and let coverage judge every answer.

Three insertion points in the fuzzing loop:

  • Grammar, once per protocol → structure-aware mutation
  • Seeds: add the message types the recorded traces lack
  • Plateau: coverage stalls → "what message comes next?"

Result vs. AFLNet, six servers: +47.6% state transitions, nine zero-days.

Source: Meng et al., "Large Language Model guided Protocol Fuzzing," NDSS 2024.

Position ChatAFL as the "LLM as semantic helper" paper — the approachable bridge from AFL-style coverage to LLM guidance. Do not teach it as "the LLM finds bugs." The fuzzer still does high-throughput exploration, the LLM supplies grammar and state hints, and coverage is the objective feedback. Walk the three insertion points: Algorithm 1 in the paper shades exactly the lines that differ from AFLNet, and that shading is the whole contribution.

Details now off the slide: nothing is trusted as-is. The grammar is majority-voted over repeated prompts, and every generated message still runs against the real server. The plateau trigger is 512 inputs with no new coverage. Full numbers: +47.6% state transitions, +29.6% states, +5.8% branches over AFLNet on six ProFuzzBench servers; nine zero-days in Live555, ProFTPD, and Kamailio, seven potentially RCE; AFLNet found 3 of them, NSFuzz 4.

Bug #1 (heap use-after-free in Live555) is the worked example: it needs SETUP → PLAY → PAUSE → PLAY, PAUSE was absent from every AFLNet and NSFuzz seed, and the LLM added it during seed enrichment and predicted it again when the fuzzer was stuck in the PLAY state.

Tool-using agents — PentestGPT and Project Naptime

PentestGPT — USENIX Security 2024 (Deng et al.)

  • Benchmark first: 13 HackTheBox / VulnHub machines, 182 sub-tasks
  • Plain LLMs do the pieces but lose the overall picture and fixate on the latest output
  • Fix: a Pentesting Task Tree owned by a Reasoning module; Generation writes the commands, Parsing condenses tool output

Project Naptime / Big Sleep — Project Zero, DeepMind

  • Code browser, debugger, Python sandbox, verifier
  • Industrial case study, not a benchmark
  • Every claim checked by concrete execution

Both are the CRS loop (explore → observe → reason → act → validate); the hard part is keeping state across many tool calls. SWE-agent made the same point: the agent-computer interface decides what the agent can find.

Sources: Deng et al., PentestGPT, USENIX Security 2024; Project Naptime; SWE-agent, NeurIPS 2024.

Teach the ordering for PentestGPT: the benchmark came first, and the architecture is a direct response to the two failure modes it exposed (context loss, recency bias). Numbers if asked: sub-task completion +228.6% over GPT-3.5, +58.6% over GPT-4; 4 of 10 real HackTheBox challenges solved. The three modules are each their own LLM session: Reasoning (lead tester) owns the task tree and picks the next sub-task; Generation (junior tester) turns it into exact commands; Parsing condenses tool output, source code, and web pages before they enter context. The task tree is exactly the state that "just ask an LLM" lacks in the CRS loop figure. Use Naptime as an industrial case study, not as a top-conference academic system. Neither is a fuzzer or symbolic execution. The shared lesson across all three: what the agent can see and do shapes what it can find. The interface to the computer is a design decision, not a detail.

In the wild: autonomous pentesting agents

Target in scope: a web app, black box. Goal: a finding the validator will sign.

Act 1: GET /api/preview?url=http://canary-7f3a.example/

This is a composite, not a description of any one product. Several commercial systems publish enough to see the shape: an LLM agent driving standard web tooling (proxy, crawler, headless browser, scripting sandbox) in a ReAct-style loop; many agents in parallel per target, each chasing one vulnerability class; and a validator per class that has to reproduce the finding before it is reported. One such system topped a HackerOne leaderboard in mid-2025 after submitting on the order of a thousand reports over a few months, with human pentesters reviewing findings before submission; the validators are what made that volume possible without burying triagers in false positives. Say "systems like this" rather than a company name.

Use the trace as the worked example. The canary callback in Obs 1 is the machine-checked edge: the target's server, not the model, made that request. The metadata endpoint in Obs 2 is what turns "SSRF" into "impact". Act 3 is the validator replaying the exploit from a clean session so a stale cookie or a lucky race cannot count.

Contrast with the source-level systems: there is no harness, no sanitizer, and no coverage signal, so the validators have to be built per vulnerability class (a canary for SSRF, a browser that actually executes the payload for XSS, an extracted canary row for SQLi). No fuzzer or solver in this loop, which is itself a data point for the "does SMT still matter" question: for black-box web targets the cheap oracle is the live server, and the strings/regex theories from the useful-theories slide rarely get called.

PANGOLIN: LLM-recovered specs for firmware fuzzing

Venue: USENIX Security 2026 — Jia et al. Targets the web interfaces of IoT firmware. Core idea: real firmware crosses language boundaries (C binaries calling Lua/PHP/shell scripts) and its reachable interfaces are undocumented. A fuzzer cannot test a format nobody wrote down, so the LLM recovers the spec and the fuzzer tests against it.

  • Entry map (§4.1): statistics isolate the dispatch code; the LLM reads only that and maps every URI, hidden ones included, to its handler
  • Parameter spec (§4.2): one agent prunes the cross-language call graph down to parsing and sanitizer calls; another writes a JSON spec per URI, marking each field Muta or NoMuta
  • Correction loop (§4.3): the fuzzer keeps NoMuta fields fixed and mutates the rest on the real device; a response that contradicts the spec goes back to the agents
Neural steps propose the entry map and the spec; the concrete step, the device, decides. A wrong spec finds nothing, and that silence is the signal.

Results: 68 zero-days, 45 of them on hidden interfaces (EAGLEYE found 4); 2.96× the previous best, LABRADOR.

Source: Jia et al., "PANGOLIN: Fuzzing Multilingual IoT Firmware with LLM-Driven Code Analysis," USENIX Security 2026. Press down for the paper's own overview figure.

The story is not "LLM finds firmware bugs." It is: the LLM recovers the spec that was never written down (interfaces, parameter formats), and the fuzzer does the actual testing against that spec. If the recovered spec is wrong, the fuzzer finds nothing, which is the signal that the neural step misfired. This is very close to the CRS architecture we have been building: neural proposes, concrete decides. The sub-slide below has the authors' Figure 4 if anyone wants the full pipeline.

Details worth saying aloud:

  • The dispatch functions are found statistically, not by the LLM: split the public URIs from traffic into strings, count them per function, and the functions with a frequency jump are the dispatch code. Only those get handed to the LLM, with three few-shot dispatch patterns (registration function, data segment, filename).
  • Pruning is what makes the cross-language call graph fit a context window: from each handler point the agent keeps at most three callees per hop, and only calls that parse parameters or sanitize them.
  • The spec labels each field Muta or NoMuta. Routing keys and format-checked values are NoMuta and never mutated; that is what gets requests past the parser. Weakly sanitized fields get a vulnerability type and a payload.
  • A sequence-recognition step groups URIs that depend on each other (login before configure), so the fuzzer sends them in order.
  • The correction loop feeds pruned-MCG nodes, the generated spec, and error output back for the first N rounds; a response that contradicts the spec is the signal that a neural step hallucinated.
  • Numbers: 68 0-days, 45 on hidden interfaces (EAGLEYE found 4), 2.96x LABRADOR, 31 IDs assigned at time of writing.

The DARPA AIxCC Competition

Final round, DEF CON 33, August 2025. Seven fully autonomous CRSs, no human in the loop, against 70 vulnerabilities injected into OSS-Fuzz-style C and Java projects (SQLite, libxml2, FreeRDP, Apache Tika, ZooKeeper, …).

What a CRS had to submit

  • PoV: an input to a named fuzz harness that trips a sanitizer when the organisers replay it
  • Patch: must build, pass the project's own tests, and stop the PoV; no human reviews it
  • SARIF triage: label a static-analysis report true or false
  • Targets arrive as a full scan of a repository or a delta scan of one commit
  • An accuracy multiplier penalised rejected PoVs and broken patches, so guessing costs!

Scoring in the final rules weighted a patch far above a PoV (6 points vs 2, with 1 each for SARIF assessment and for bundling PoV, patch, and SARIF together; verify against the published rules), and the whole score was multiplied by an accuracy term, which is why the systems had to be conservative about what they submitted. The point for us: discovery, proof, patch, and validation were each scored separately, which is exactly the evidence separation the synthesis section argues for.

Viewing a single bug through from POV of many tools...

Back to the very first example:

char buf[64];
if (len < 64 && magic == 0x41424344) {
  memcpy(buf, input, len + 16);
}
Fuzzing supplies ground truth. Symbolic execution phrases the question. SMT answers it. The LLM does the guessing.
  1. Fuzzer. Millions of runs a minute, but a random 4-byte magic matches once in 232. Coverage stalls at the if.
  2. Symbolic execution. Re-runs a stalled input concolically. Path condition to the memcpy: len < 64 ∧ magic = 0x41424344.
  3. SMT. Bit-vector query, milliseconds: SAT with magic = 0x41424344, len = 0. If you know the safety property, ask it directly: len < 64 ∧ len + 16 > 64 is SAT with len = 49.
  4. Fuzzer. The model is a seed. It passes the check; a few mutations of len later, ASan reports a stack-buffer-overflow at the memcpy. Input + report = PoV.
  5. LLM. Reads the report and the function, names the cause (the check bounds len, the copy uses len + 16), proposes len + 16 <= sizeof buf, writes a regression test.
  6. Validator. Build, tests, replay the PoV: no crash. Fuzzing restarts on the patched binary.

This is the synthesis slide: the four engines the lecture promised, on the very first example from the goal slide, with the CRS loop figure as the map. Build with the arrow keys.

Emphasise the cost story at each step. Mutation is free but blind: a 4-byte magic value is a 1-in-4-billion event for a random mutator, which is why coverage stalls. The solver is exact but only answers the question it is asked, so someone has to phrase the path condition, and, if you know the safety property, the violation condition too (step 3's second query is the same shape as the examinable path-condition slide). The fuzzer then confirms the model by execution, which is the only evidence that counts; note that the solver's first model (len = 0) does not crash, and that is fine, because behind the gate the bug is shallow and the fuzzer finds it in seconds. That is Driller's "compartments" argument in miniature. The LLM enters at the point where reading is required: what the check was supposed to enforce, and what patch preserves that intent without breaking the tests. The validator is the same machine-checked edge as in the CRS figure.

Static analysis (next lecture) would flag len + 16 against sizeof buf without running anything, at the price of false alarms, and a real CRS would use it to point the fuzzer at this function in the first place.

Ask the room: which of the six steps could an LLM do alone, and which would you refuse to take its word for?

So, does SMT still matter?

Yes, as a component, not the driver. Each engine is trusted for something different:

  • Fuzzing: cheap and never wrong, but blind.
  • Symbolic execution + SMT: exact, and can say "no such input exists," but can't prove
  • LLM: great at guessing, use in a loop with conventional tools

To me, the big question is: how does LLM+X change the game versus traditional tools?

Close the loop with the question from the "Is SMT really AI?" slide and the Section 2 divider. The answer is "yes, as a component, not as the driver." Each engine is trustworthy along a different axis; the LLM is the only one that reads meaning but also the only one that is routinely wrong. Every system in this lecture is arranged so the wrong-able engines only propose and the exact or concrete engines decide.

Evidence if asked: HLPFuzz calls the LLM only for the branch that concolic execution and SMT cannot model, and still runs the same propose-then-check loop. QSYM already traded soundness for speed because the fuzzer checks answers for free; an LLM is that trade taken further. At AIxCC, fuzzers found the bugs, LLMs wrote harnesses, seeds, triage, and patches, and validators scored all of it. No system replaced the validator.

If a student pushes on "why not just LLM + fuzzer, drop the solver": a magic value or a length relation is a millisecond for a bit-vector solver and a coin flip for a language model, and the solver's UNSAT is a proof that the fuzzer should stop wasting time on that branch. Conversely the solver cannot write a valid JSON body or guess that PAUSE comes after PLAY. Different questions, different oracles.
